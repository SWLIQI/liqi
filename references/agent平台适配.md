# Agent 平台适配（v5.11.0）

> **这份文件管什么**：liqi 在**非 WorkBuddy 环境**里怎么跑——脚本跑不了时怎么办、
> 上下文不够时加载哪些、各平台的落点差异。
> **这份文件不管什么**：🔴 **不改任何规则、不改任何门禁判据、不改任何机检码。**
> 平台只影响「谁去查」与「加载多少」，**不影响「查什么」与「判据是什么」**。
> 换句话说：**换平台不换标准。** 任何平台都不得以「跑不了脚本」为由放宽一条规则。

---

## 〇、为什么要有这份文件

liqi 的机检是它的护城河（内容规则码数量以 `check_skill.mjs` 第二项两向对照为准 + 项目级十门 + L4 契约核销），
但**护城河只在能执行 `scripts/` 的环境里存在**。真实情况是有相当一部分用户
在 Coze / Dify / 豆包这类平台上用 liqi——那里没有 Node、没有 Python、
有的连多文件加载都受限。

没有这份文件时，这类环境下会出现两种典型失败：

1. **卡死**：执行者发现跑不了脚本，不知道该怎么办，停下来催环境；
2. **假装通过**：跳过机检，但交付文档里照样写「已校验 / 全绿」——
   这正是 liqi M 轴四铁律第 3 条要治的那个病（**禁止声称「已核验」而实际从未见过图**），
   在平台维度上同一个病会再犯一次。

所以这份文件给的**不是降级标准，是降级路径**：谁去查可以换，查不查不能换。

## 一、平台能力四维矩阵

判定一个环境，只看四维。填完这四格，后面所有取舍都自动定了。

| 维度 | 问什么 | 决定了什么 |
|---|---|---|
| ① **能否执行脚本** | 有没有 Node + Python，能不能跑 `scripts/` | 机检是机器跑还是人工跑（第二节 vs 第三节） |
| ② **能否多文件加载** | 能不能一次读多份 `references/` | 走完整 Load Map 还是最小加载集（第五节） |
| ③ **上下文窗口** | 能装多少 | 一次加载几份（第五节） |
| ④ **能否落盘** | 能不能写文件（`.gates.jsonl`、台账、核销表） | 门效统计与台账能否持久化 |

| 平台类型 | ①脚本 | ②多文件 | ③上下文 | ④落盘 | 走哪节 |
|---|---|---|---|---|---|
| **WorkBuddy**（原生基准） | ✅ | ✅ | 大 | ✅ | §四·1 |
| **本地 CLI / IDE 型**（Claude Code、OpenClaw 类） | ✅ | ✅ | 大 | ✅ | §四·2 |
| **工作流编排型**（Coze、Dify） | ❌ / 受限 | 受限 | 中 | 部分 | §四·3 |
| **通用对话型**（豆包、网页端对话） | ❌ | ❌ | 小 | ❌ | §四·4 |
| **节点式自动化**（ComfyUI、Canvas 工作流） | 部分 | ❌ | 小 | ✅ | §四·5 |

⚠️ **这张表不是能力排行榜**。WorkBuddy 之外的平台只是**执行环境不同**，
交付标准完全一致——§二的通用铁律在任何一格都成立。

## 二、三条通用铁律（任何平台都不可省）

### 铁律 1 · 前置锁四项不可省、不可默认

第零道锁（〇 赛道分流）+ 锁① 模型版本 + 锁② 画幅 + 锁③ 投放面/风格轨道/交付形态。
**四项缺一项就停下问用户，禁止默认值**——这条不因平台变化而放松。

理由（liqi 全库口径）：赛道决定「这一类内容该怎么写」，是语速 / VO 容量 / 资产口径 /
字幕的上位口径；模型版本决定段头骨架与时长红线。**这两样在哪个平台上都是源头**，
源头错了，下游再怎么补都补不回来。

### 铁律 2 · Load Map 一份一份加载，不因平台开例外

`SKILL.md` 的 Load Map 明确要求「按需取 1–2 份，不要一次加载全部」。
在小上下文平台上这条**更硬**——不是"可以少读几份"，是"必须按当步只读那一份"。
见 §五 最小加载集。

🔴 **禁止用平台的「总结 / 压缩 / 摘要」替代读规则原文。**
压缩会丢掉三类东西：**规则码名、数值区间、否定式措辞**。这三类恰恰是 liqi 规则里
最不能丢的部分（配额区间 25%~40%、IAU 上限、lock_out 禁写词全是这三类）。
丢了之后执行者会以为"没写这条规则"，于是漏判——**这是最隐蔽的一类假绿**。

### 铁律 3 · 🔴 不得声称「已校验」

M 轴四铁律第 3 条是「禁止声称『已核验 / 与资产册一致』而实际从未见过图」。
**同一条纪律在平台维度上原样适用**：

| ❌ 禁止写 | ✅ 应该写 |
|---|---|
| 「已通过机检」 | 「未跑机检 · 人工核对 8/10 项 · 未覆盖：G 门台账对账、N 门剧本门禁」 |
| 「0 error / 0 warning」 | 「机器校验未执行，按 §三 人工清单逐项核对，结论如下」 |
| 「校验通过」 | 「人工核对完成，未覆盖项已声明」 |
| 「CT7 PASS」 | 「CT7 = N/A（无脚本环境，机检未执行）」 |

**没有跑过脚本，就不许出现任何"通过 / 绿 / PASSED"字样。**
报"没查"永远比报"查过了"安全——这是 liqi 从 Z 门、S0、S22、G7、N2/N3、F7
一路立下来的同一条口径。

## 三、无脚本环境的降级路径

**降的是"谁去查"，不是"查不查"。** 十门 + 风格层 + L4 契约层，
每一门都有对应的人工核对动作，一个都不少。

### 3.1 十门人工核对清单

| 门 | 机器查什么 | 人工核对什么（无脚本时） |
|---|---|---|
| **A 台词一致性** | 剧本台词 vs 稿内 `对白：` 行 | 逐条比对，**对白零擅删**；重点看长句有没有被截断 |
| **B 资产锚覆盖** | 出场角色/道具是否都有 `@锚点` | 逐镜点名，确认每个出场对象都有锚点且描述与资产册一致 |
| **C 版本漂移** | 同镜出现两个版本名 | 同一角色跨镜的**版本名 / 服装 / 色值**是否只有一个版本 |
| **C2 场景时段漂移** | 声明时段 T 却写了 T 的禁写词 | 逐段看：声明时段 × 该时段 `lock_out` 里的词有没有出现 |
| **D 时长一致性** | 各镜时长合计 vs 段总长 | 手算：各镜时长之和 = 段长；**台词字数 ÷ 语速档 ≤ 镜长**（语速取实测校准表，别用理论档） |
| **E 转场表完整** | 每个转场点有注记 | 逐段检查转场注记是否齐全、方式是否写明 |
| **F 资产层纪律** | 图号 ∈ 接线单 / M0 无图号 | 按素材形态核对：M0 不得出现图号；M1/M2 每个图号在《素材接线单》里都有行 |
| **G 台账对账** | 台账 vs 提示词（需 `--ledger`） | 逐段比对**持物 / 时段 / 变更落点**三样；**没有台账就是没查，不是通过** |
| **N 剧本量化门禁** | 场序号 / 情节点密度 / 事实权威链 | 场序号唯一且连续；情节点单集 ≥5 且每 15s ≥1；改编稿有五级标注 |
| **S 分镜配额** | 11 项区间配额 | 逐镜标景别与机位角度后人工统计 Q1~Q11 |

**风格层**：全包只有一个主 style_id；正文用色不越该锚 `palette`；不出现该锚 `negative_direction` 的禁用项。
**L4 契约层**：CT1~CT8 逐项自评；**缺项写 N/A + 理由，不许写 PASS**。

### 3.2 门禁态怎么写

无脚本环境下，交付文档里的门禁段必须长这样：

```text
【机检状态】未执行（当前环境无 Node/Python，无法运行 scripts/）
【人工核对】8 / 10 项已完成
【未覆盖】G 门（台账对账，需 --ledger）· N 门（剧本门禁，需 --script）
【结论格式】本包未经机器校验，以下结论均为人工核对
```

🔴 **"未覆盖"清单必须写出来**。写「已人工核对」却不写覆盖了哪几项，
和写「已通过」是同一个病——读者无法判断没提的那些门是过了还是根本没查。

### 3.3 CT7 怎么填

`audit_contract.py` 的 **CT7（投喂稿过机检）** 在无脚本环境下填：

```text
CT7：N/A —— 无脚本环境，`check_prompt.mjs` / `audit_project.py` / `check_style.mjs` 均未执行；
      已按 agent平台适配.md §三 人工核对清单完成 8/10 项，未覆盖 G / N 两门。
```

🔴 **N/A 不是通过，是「没查」**（合同层既有口径，见 `质控层_门禁与过审.md` §10.3）。
核销率的分母不含 N/A，所以填 N/A 会把这一项从通过项里扣掉——
**这是它应有的代价，不要为了核销率好看去填 PASS**。

### 3.4 `.gates.jsonl` 落不了盘怎么办

门效统计（哪道门最常响、哪道门从没响过）依赖落盘。落不了盘时：
在交付文档里**手写一张门次统计表**（门名 × 命中次数 × 典型样例），下次同项目复用。
数据粗一点没关系，**有数据才能反推规则迭代**——这是 liqi 迭代方式的核心，别丢。

## 四、各平台具体路径

### 4.1 WorkBuddy（原生基准）

现状即基准，无需任何调整：Load Map 完整可用、19 个脚本全可跑、
`--ledger` / `--beats` / `--script` / `--registry` / `--combat` / `--mode` 全参数可用。
**本文件不改变 WorkBuddy 上的任何既有行为。**

### 4.2 本地 CLI / IDE 型（Claude Code、OpenClaw 类）

能力等同 WorkBuddy（①②③④ 全 ✅）。唯一差异是**没有图形化选择界面**，
前置锁四项要靠对话问出来——注意不要用"最常见"当默认值（赛道① 最常见但仍必问）。

### 4.3 工作流编排型（Coze、Dify）

| 项 | 处置 |
|---|---|
| 脚本 | 通常 ❌。走 §三 人工核对清单 |
| 多文件加载 | 受限。把当步需要的 reference **内联进提示词或知识库**，不要指望它自己找文件 |
| 上下文 | 中。按 §五 最小加载集走 |
| 落盘 | 部分。有就用，没有就按 §3.4 手写门次统计 |
| **额外注意** | 工作流节点之间会**丢失上下文**——把前置锁四项与素材形态声明写在**每个节点的输入里**，不要只写在第一个节点（"逐单元投喂，所以每个单元必须自足"这条信念在节点式平台上同样成立，而且是硬性的） |

### 4.4 通用对话型（豆包、网页端对话）

能力最弱（①②③④ 全 ❌ 或小）。处置原则：

1. **缩小任务粒度**：不要一次要一整集，按**段**（15s）为单位出，出一段验一段；
2. **一次只带一份 reference**：当前步骤需要哪份就只带哪份；
3. **规则内联**：把当步会用到的**数值区间与禁写词**直接写进提问里，
   不要指望模型记得住上一轮读过的文件；
4. **机检全走人工**：按 §三 清单逐项核，并如实写未覆盖项；
5. 🔴 **连续对话会衰减**：超过约 10 轮后开新会话，并把前置锁四项与风格 id 重新声明一遍。

### 4.5 节点式自动化（ComfyUI、Canvas 工作流）

脚本部分可用、落盘可用、但**多文件加载与上下文都受限**。
处置同 §4.3，额外一条：**把 liqi 的产出当"提示词文本"在节点间传递**，
不要用节点逻辑去替代 liqi 的规则判断——节点能编排流程，判不了语义。

## 五、最小加载集（小上下文平台）

小上下文环境下，**任何时刻只装这四样**，多一份都不带：

| # | 内容 | 为什么不可省 |
|---|---|---|
| 1 | **前置锁四项的结果**（赛道 / 模型版本 / 画幅 / 投放面+风格轨道+交付形态） | 决定后面所有数值口径；丢了就只能猜 |
| 2 | **`SKILL.md` 当前 Step 的正文**（只带那一步，不带全文） | 流程与硬规则在那里 |
| 3 | **当前步 Load Map 指定的那 1–2 份 reference** | 举例：Step 2.5 → `资产层_锁定与一致性.md`；打戏镜 → `专项_打斗编排.md` |
| 4 | **当次任务的风格锚**（投 2.5/2.0 面时）或 **H3 适配**（投 H3 面时） | 色域 / 禁用项 / `heads_range` 都在锚里，没有它正文会串轨 |

**切换规则**：换一步就换掉第 2、3 项，**第 1、4 项全程保留**。

⚠️ **第 4 项最容易在切步时被丢掉**，而它丢了之后的症状是"正文用了不该用的颜色/
写了禁用项"——这类错误在人工核对里很难发现（因为要拿锚去对），所以**务必全程保留**。

## 六、禁止的做法（四条）

| # | 禁止 | 为什么 |
|---|---|---|
| 1 | **因跑不了脚本就放宽规则** | 换平台不换标准。放松一条，后面的门就都失去意义 |
| 2 | **把降级写成通过** | 见铁律 3。报"没查"永远比报"查过了"安全 |
| 3 | **为某个平台新建专属规则集** | 平台只加**适配路径**，不加**规则分叉**。分叉一次，维护成本翻倍，且很快会出现"同一条规则两个版本" |
| 4 | **用平台的摘要/压缩替代读原文** | 见铁律 2。丢的是规则码名、数值区间、否定式措辞——正是规则里最不能丢的部分 |

## 七、自检四问（任何平台交付前都过一遍）

1. **前置锁四项都问了吗？** 有没有哪一项是我替用户默认掉的？
2. **有没有出现「已校验 / 已通过 / 全绿」而实际没跑过任何脚本？**（有就立刻改）
3. **降级项有没有写明"未覆盖什么"？** 只写"已人工核对"等于没写。
4. **CT7 填的是 N/A + 理由，还是 PASS？** 没跑机检却填 PASS 是契约造假。

## 八、与既有机制的关系（别把这份文件当第五道锁）

| 既有机制 | 本文件的位置 |
|---|---|
| **前置锁（第零道锁 + 三锁）** | 不变、不增。本文件**不新增第五道锁**，只规定在各平台上怎么把四项问出来 |
| **M 轴素材形态 M0/M1/M2** | 铁律 3 是 M 轴四铁律第 3 条在平台维度的延伸，口径同源 |
| **契约核销 CT1~CT8** | 只影响 CT7 的填法（§3.3），**不改任何契约项的判据** |
| **假绿防线（Z/S0/S22/G7/N2/F7）** | 铁律 3 与 §3.2 是同一条口径在平台层的延续 |
| **Load Map** | 只在 §五 给小上下文环境的加载顺序，不改 Load Map 本体 |

**倒车防护**：本版不推翻任何既有裁决——WorkBuddy 上行为零变化；
规则码数量与判据均不变；前置锁仍是四项不加不减；
风格锚递进收窄与冻结规程不变；M 轴四铁律不变。

## 九、来源与可信度

- **问题来源**：20 邻域对标（2026-10-16）中「多平台 / 多 Agent 适配」一项 liqi 6.0 / 老李 8.5，
  是 liqi 唯一"非创作类"的大缺口，也是改造成本最低的一项。
- **参照**：上游 `short-drama-director` V7.4.20 的 `agent-platform-adapters.md`
  （覆盖 OpenClaw / WorkBuddy / 豆包 / Coze / Dify + Canvas / ComfyUI）。
  **liqi 只取其"适配"思路，不取其规则内容——本文件不含任何上游规则。**
- **liqi 自己的加码**（上游没有的两条）：① **铁律 3 不得声称已校验**（把 M 轴四铁律
  延伸到平台维度）；② **CT7 的 N/A 填法**（把契约层的 N/A 语义接到平台场景上）。
  这两条是 liqi 相对上游更严的地方。
